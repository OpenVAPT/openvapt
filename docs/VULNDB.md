# Offline Vulnerability Snapshot

The snapshot committed to the repository is a small, hand-written test fixture (`Fixture: true`). It carries no advisory data, so on a build that embeds it HOST-CVE-001, HOST-CVE-002, HOST-CVE-003 and WEB-CVE-001 report Incomplete with the evidence line "No advisory data: the embedded snapshot is test fixture data", never Pass. `make vulndb` runs cmd/vulndbgen into the embed path (`internal/vulndb/data/snapshot.json.gz`); the release workflow does the same before building. Every report header shows the snapshot date, advisory count and age in days; a snapshot older than 90 days is flagged in the header and by HOST-CVE-003 (Low), never as a failure of the scan.

The simulated labs (`openvapt demo`, engine tests) carry their own illustrative snapshot in memory (`internal/lab/fixtures_vulndb.go`), so the lab behaves the same whichever snapshot the binary embeds.

Ecosystems: Debian 11 to 13, Ubuntu 20.04 to 24.04 LTS, AlmaLinux and Rocky Linux 8 to 10, Alpine 3.20 to 3.24, Packagist, npm, PyPI, RubyGems, Go and crates.io. OSV publishes no WordPress export (checked against https://osv-vulnerabilities.storage.googleapis.com/ecosystems.txt on 2026-10-14), so WordPress core found through `wp-includes/version.php` is inventoried but reported Incomplete by WEB-CVE-001 until a WordPress feed exists; the WordPress version comparator is kept for that day. Every CVE finding names its matcher: "exact version" (the version is listed by the advisory), "range" (OSV range evaluation with the ecosystem's version ordering) or "heuristic" (the version was read from a file header, such as a jQuery banner, rather than a package record). WEB-CVE-001 reports Incomplete for an inventoried ecosystem the snapshot has no advisories for, instead of a silent Pass.

The release pipeline runs cmd/vulndbgen with -out and -ecosystems and keeps every package with a rated advisory, or one listed in KEV. Advisories with no rating at all are left out, so absence of a finding does not mean no CVE applies. The snapshot carries ids and aliases, severity, CVSS score and vector, module streams and affected ranges; summaries, references and dates are dropped to keep it small, and distribution version lists are dropped where ranges cover them. A full build on 2026-11-04 was 86,674 advisories, 7.9 MB compressed, about 375 MB peak memory on arm64 macOS. The optional -packages file limits a build to named packages, which can then fail the empty-ecosystem rule by design. A configured ecosystem that yields no advisories fails the build, and withdrawn records are dropped. Runtime scans use only the embedded gzip file and never access the network. The generator reads OSV ecosystem export ZIPs and the CISA KEV JSON feed. 

Sources and licence metadata: OSV ecosystem exports at https://osv-vulnerabilities.storage.googleapis.com/ are aggregated by OSV, and each advisory is licensed by its originating database (GitHub Advisory Database advisories under CC BY 4.0; Debian, Ubuntu, AlmaLinux and Rocky Linux records under their security teams' terms). The CISA KEV catalogue at https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json is a work of the United States Government (public domain in the United States). The snapshot header records these statements and `openvapt version` prints them; THIRD_PARTY_NOTICES.md carries the notice.

Matching tries both the binary name and the source package name, because Debian, Ubuntu and Rocky Linux file advisories under the source name (from the dpkg Source field and rpm SOURCERPM). dpkg packages match by source only, signed kernels (linux-signed*) match as linux at the binary version, and an rpm subpackage matches its source at the source version, with the epoch taken from a sibling package; with no such sibling the source match is skipped, which can miss an advisory. Rocky and AlmaLinux module builds match by module stream, read from the erratum summary and the rpm MODULARITYLABEL; when either is unknown they match only within the same leading version number. Rows are grouped by source package and advisory, so a finding names the source package. Web discovery covers configured document roots, then /srv and /opt, and recognizes composer.lock, package-lock.json versions 1 through 3, poetry.lock, Pipfile.lock, requirements.txt, Gemfile.lock, go.mod, Cargo.lock, wp-includes/version.php, and a best-effort jQuery header. Missing lockfiles or truncated reads make coverage incomplete.

## Severity and KEV Rules in the Generator

- KEV status is set when the record's ID, any alias or any `upstream` identifier is in the CISA KEV feed. Debian records (DEBIAN-CVE-*) name their CVE only in `upstream`.
- Severity uses the first valid CVSS v3 vector. Without one, a CVSS v4.0 vector is rated conservatively without the official macrovector table, rounding up so nothing is under-rated: critical when the attack is network, low complexity, no attack requirements, no privileges, no user interaction and the vulnerable system impact is High; high when any vulnerable or subsequent system impact is High; otherwise medium. An unparsable v4 vector is rated high so it is kept. Only CVSS v3 fills the score and vector fields.
- Without any CVSS vector, an Ubuntu priority of critical or high is used as the severity; medium and low keep their word, and negligible counts as low.
- AlmaLinux records have no severity field, so a summary opening "Critical:" or "Important:" rates them critical or high, and "Moderate:" or "Low:" medium or low.

## Generator Limits

Downloads are HTTPS only, including redirects, streamed to temporary files with a 1 GiB cap per file (checked against Content-Length first, then while copying), with a 15 minute timeout. Ecosystems are processed one at a time and only one export is kept on disk. A record over 4 MiB, more than 2,000,000 records or more than 8 GiB of uncompressed records in one export is an error. Parse failures are counted and reported per ecosystem, and more than 1% fails the build.
