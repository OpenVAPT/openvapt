Standards and Methodology

How OpenVAPT lines up with the public frameworks that vulnerability assessments are judged against, and where it deliberately stops.

Methodology: NIST SP 800-115

NIST SP 800-115 describes four phases of a technical security assessment. OpenVAPT implements three and leaves the fourth out on purpose.

PhaseIn OpenVAPTWhere in the Code
PlanningScope is fixed in code to the machine the tool runs on. Rules of engagement are the EULA and the terms prompt at every scan.internal/scope, cmd/openvapt
DiscoveryRead-only collection: OS release, packages, sshd configuration, kernel parameters, listening sockets, local websites.internal/checks/collect
AttackNot implemented, by design. No exploitation, payloads, brute force or denial of service. This is what makes OpenVAPT an assessment, not a penetration test.None
ReportingScope, methodology, findings with severity, evidence, remediation and verification, then limitations.internal/report

Severity: CVSS v3.1

{{chartTable $d.ChartData "severity" "Checks by Severity"}}

Every check carries a representative CVSS v3.1 base vector and the matching qualitative rating from the FIRST CVSS v3.1 specification: Critical 9.0-10.0, High 7.0-8.9, Medium 4.0-6.9, Low 0.1-3.9. The vector reflects a typical internet-facing server. Your own environment can raise or lower the real risk, which is why the report states this limitation.

Report Formats

Reports follow the structure recommended in NIST SP 800-115 section 8 and are written in open formats: self-contained HTML (prints to PDF), JSON (schema openvapt.report/1), OASIS SARIF 2.1.0 for code-scanning tools, and Markdown.

Benchmarks and Copyright

Some checks cover the same topics as CIS Benchmarks. OpenVAPT names the topic only and writes its own explanations; it does not copy benchmark text, which is licensed by CIS.
